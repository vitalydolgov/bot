# Local agents

`local-agents` is a local stand-in for `agents serve` and `agents chat`. The hosted commands register the agent with Mistral's control plane and poll its task queue; sessions and their events live on the service. `local-agents` keeps the same shape without the service: a SQLite file holds the agent registry, the sessions, a command queue and an event log, and a worker polls it. Nothing is registered with Mistral and the Session API is not used, so only the model endpoint key from `.bots/config.toml` is needed.

## Commands

```sh
uv run local-agents serve                  # register every profile found in .bots/profiles/ and poll for work
uv run local-agents serve --profile grad   # serve only grad
uv run local-agents chat                   # resume the latest session (or start one)
uv run local-agents chat --new             # start a fresh session
```

### `serve`

Discovers the profiles to serve and loads each from `./main.py` (override with `--path`):

- The common config `.bots/config.toml`, served as `bot`.
- Every `.bots/profiles/<profile>/config.toml`, served as `<profile>`.

Each profile is loaded with `BOT_PROFILE` set to its name, so it gets its own configuration and memory. A profile that fails to load is skipped with an error; the rest are served. Stop it with Ctrl+C. The agents stay registered but receive no sessions until you serve them again.

- `--profile <name>` serves only that profile.
- `BOT_PROFILE` set in the environment serves only that profile.

The command queue is partitioned by agent: the worker claims only commands for the agents it serves, so profiles never run each other's sessions.

### `chat`

Talks to a served agent. The agent argument is optional and defaults to `bot`.

| Flag | Description |
| --- | --- |
| `-m`, `--message` | Send a single message and exit. Without it, an interactive prompt opens; Ctrl+D or `/exit` quits. |
| `--new` | Start a fresh session instead of resuming. |
| `--resume` | Resume a specific session, by either of its ids (see below). |
| `--delete` | Delete a session, by either of its ids, and exit. Removes its rows from the store. |

Exiting the chat detaches from the session; it stays resumable. By default `chat` resumes the most recent session for the agent that has been started at least once.

## How it works

The worker and the chat client never talk to each other directly. They communicate through the store:

- The chat client enqueues commands (`start`, `resume`, `message`, `detach`) and polls the event log.
- The worker polls the command queue, claims one command at a time, runs the turn in-process through the SDK's local runtime, and appends events (`reply`, `tool_call`, `tool_result`, `notice`, `turn_done`, `error`, ...).
- The client prints events as they appear.

Sessions are journaled to `.bots/sessions/<sdk_id>/` on every committed state transition, not just at shutdown, so a session survives worker restarts and can be resumed in a later process.

Each session has two ids:

- the **store id**, generated by the client and used as the primary key in the store;
- the **SDK session id** (`sdk_id`), assigned when the session starts and used as the journal directory name.

`--resume` and `--delete` accept either. The chat banner prints the SDK session id.

## State

All state lives under `.bots/`:

- `.bots/local_serve.db` — the store: agent registry, sessions, command queue, event log. The filename predates the `local-agents` rename and is kept so existing sessions carry over.
- `.bots/sessions/` — one journal directory per SDK session id.

Deleting both resets all local state.

## Limitations

- **Approvals are auto-denied.** The worker cannot prompt, so any tool approval request is denied and reported as an `approval_denied` event.
- **One process per session.** A session journal is locked while open; a session already open in one process cannot be opened in another.
- **Single machine, single worker.** There is no hosted chat link and no multi-worker coordination. The command queue is claimed atomically, but the journal lock is what actually serializes access to a session.
- **Experimental SDK API.** Session journaling uses an experimental SDK surface; the CLI silences the experimental warning by setting `AGENTS_SDK_EXPERIMENTAL_WARNINGS=0` before loading the SDK.
